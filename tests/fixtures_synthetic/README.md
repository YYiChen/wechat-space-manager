# Synthetic WeChat filesystem fixtures

`build_fixture.py` constructs a small, deterministic `xwechat_files`-like tree.
Every byte is generated by the script. Names are deliberately synthetic and the
`*.dat`, `*.mp4`, and `*.pdf` files are sentinels, not valid user media or real
encrypted WeChat payloads.

## Build it

```powershell
python tests/fixtures_synthetic/build_fixture.py --destination .tmp/synthetic-xwechat
```

The destination must be empty or absent. The builder refuses a non-empty target.
This makes it unsuitable for pointing at a real WeChat directory.

## Phase 3 database and mapping fixture

`build_phase3_fixture.py` creates the larger deterministic fixture used by the
desktop, filtering, database-adapter and recoverable-execution work:

```powershell
python tests/fixtures_synthetic/build_phase3_fixture.py `
  --destination .tmp/synthetic-phase3 --seed 20260909
```

The generated tree contains two synthetic accounts, direct and group sessions,
2023--2026 message months, every public media type, zero/one/1 MiB size
boundaries, present/missing/changed/duplicate file observations, and
exact/high/medium/low/unmapped mapping confidence.  Protected `db_storage`,
`business/favorite`, and `SendTemp` samples are present but marked ineligible.
The generated `phase3-manifest.json` is path-free and lists every boundary and
rejection sample.  `media-records.json` is validated against the public
`MediaRecord` contract.

The same seed produces byte-identical records, manifests and SQLite files.
Three SQLite inputs are generated: `synthetic-v1` and `synthetic-v2` are
supported shapes, while `synthetic-legacy-rejected` intentionally lacks the
required media columns and must be refused by an adapter.  All database rows
contain only relative paths and opaque IDs; there are no message bodies, keys,
real contacts, or absolute paths.

## Coverage

| Case | Representative path | Expected treatment |
| --- | --- | --- |
| Two accounts | `wxid_synthetic_alpha_d729`, `wxid_synthetic_beta_d729` | Discover independently |
| Image attachment | `msg/attach/.../Image/` | Map as image candidate |
| Forwarded record | `msg/attach/.../Rec/record-alpha-0001/{0,0_t}` | Preserve original/thumbnail pairing |
| Video | `msg/video/.../clip_001.mp4` | Map as video candidate |
| File | `msg/file/.../report_001.pdf` | Map as file candidate |
| Regenerable cache | `cache/image_preview.bin` | Eligible only after a separate cache policy |
| Database | `db_storage/` | Never directly delete |
| Favourite | `business/favorite/` | Never directly delete |
| In-progress send | `SendTemp/` | Never directly delete |
| Reparse point | optional `reparse-probes/escape-link` | Do not traverse or plan for deletion |

Phase 3 files are generated under a caller-provided temporary destination and
are not checked into the repository.  The checked-in generator and acceptance
tests are the source of truth for the catalog.

The record directory mirrors the structural facts that matter for mapping tests:
it holds a message-local record ID and paired integer-name original/thumbnail
files. It does not pretend to reproduce WeChat cryptography.

## Reparse-point requirement

Run with `--with-symlink-probe` only in a disposable test directory:

```powershell
python tests/fixtures_synthetic/build_fixture.py --destination .tmp/synthetic-xwechat --with-symlink-probe
```

If Windows policy blocks symlink creation, the normal fixture remains valid and
the report records `symlink_probe_status: unavailable`. A production scanner must
reject every reparse point (symlink or junction) before traversal and must verify
the resolved path stays under the selected account root.

## Expected summary

The baseline build has 16 regular payload files totalling 1,712 bytes. The exact
paths, categories, and byte counts are in `fixture-manifest.json`. An enabled
symlink probe adds a link and external sentinel for safety tests; those are not
regular fixture payloads and are excluded from the baseline totals.
